# Plan: automatic note cache sets

## Goal

A *set* is a named group of note IDs that have some connection. The Electron sync computes a fixed list of automatic sets from the notes it just loaded (using the PC clock, so every sync is "now") and pushes them to the cache, which stores them as given and exposes read-only endpoints to view them. Nothing displays them yet.

## Scope

In:
- Four automatic sets per source: `created-today`, `modified-today`, `created-last-30-days`, `modified-last-30-days`. The file source gets only the two `modified` sets (it has no created date).
- Sets are per source: a sync replaces only its own source's sets (`bear:*` or `file:*`; every folder shares the `file` source, as with the existing delete scoping).
- Computed on every sync, even when no note changed (today and last 30 days move with the clock).
- Cache: storage, a replace endpoint (used by the sync), read endpoints, OpenAPI spec, regenerated client.
- curl testing instructions in `apps/cache/README.md`.

Out:
- Displaying sets (web or Electron), custom filter sets, scheduled sync.
- Any change to the IPC contract, `state.json` or the sync result shown in the UI.
- Deriving sets inside the cache.

Definitions (PC local time at sync): *today* = the local calendar day containing `now`; *last 30 days* = `now - 30 x 24h` or later. Notes with an empty or unparseable `created`/`modified` are left out of the matching set. A set with no members is still stored (empty).

## Technologies

Existing stack only: `node:sqlite` in `store.ts`, Hono + `@hono/zod-openapi` routes, hey-api generated client (`pnpm openapi`, `pnpm generate`), vitest. No new dependencies.

## Cache design

- Set id is a client-chosen name without `/`, namespaced by source: `bear:created-today`, `file:modified-last-30-days`.
- Tables in `store.ts`: `sets (set_id PRIMARY KEY, updated)` and `set_notes (set_id, note_id, PRIMARY KEY (set_id, note_id))`. `updated` is stamped by the service (like `synced`).
- API:

| request          | does                                                                                  |
| ---------------- | ------------------------------------------------------------------------------------- |
| `PUT /sets/:id`  | replace the set: body `{ "noteIds": ["..."] }`; response `{ "count": n }`             |
| `GET /sets`      | `[{ "id", "count", "updated" }]` ordered by id                                        |
| `GET /sets/:id`  | `{ "id", "updated", "noteIds": [...] }` (ordered), `404` if unknown                   |
| `DELETE /sets/:id` | remove a set, `204` even if it did not exist                                        |

- Deleting a note (`DELETE /notes/:id`) also removes it from every set, so sets never point at a deleted note.

## Files

- `apps/cache/src/store.ts` - `sets`/`set_notes` tables; `replaceSet`, `listSets`, `getSet`, `deleteSet`; `deleteNote` also clears set membership.
- `apps/cache/src/schemas.ts` - set id/param, replace body, list row, set detail, replace result schemas.
- `apps/cache/src/app.ts` - four set routes.
- `apps/cache/openapi.json` - regenerated by `pnpm openapi`.
- `apps/cache/README.md` - API table rows, curl walkthrough for sets, note on how the Electron sync fills them.
- `apps/cache/tests/store.test.ts`, `api.test.ts` - set behaviour, note deletion cleanup, validation, 404.
- `apps/electron/src/main/note-sets.ts` - `buildNoteSets(source, notes, now)` returning `{ id, noteIds }[]` for the source's applicable sets.
- `apps/electron/src/main/sync.ts` - `SyncOptions.now?: Date`; after pushing notes and deleting, `putSet` for each built set (always, even if nothing changed). Result unchanged.
- `apps/electron/tests/main/note-sets.test.ts`, `sync.test.ts` - day boundary, 30-day cutoff, empty/invalid dates, file vs bear, sets pushed on an unchanged sync, source scoping.
- `CLAUDE.md` - one line each in the cache and Electron sync bullets.

## Steps

1. Cache store: tables and set functions, `deleteNote` cleanup; unit tests in `store.test.ts`.
2. Cache schemas and routes (`PUT/GET/GET/DELETE`); tests in `api.test.ts`.
3. `pnpm openapi` then `pnpm generate`; check the committed spec test passes and the generated SDK has the set functions.
4. Electron `note-sets.ts` with `buildNoteSets`; `note-sets.test.ts`.
5. Wire into `syncNotes` (push sets after notes/deletes, `now` option); update `sync.test.ts` (and `ipc.test.ts` if mocks need it).
6. Docs: cache README (API rows, curl instructions: push notes, `PUT /sets/...`, list, get one, delete a note and see it leave the set, delete a set) and `CLAUDE.md`.
7. End-to-end check: run `pnpm dev:cache`, sync with the demo folder through `syncNotes` or the Electron app, and view the sets with the README's curl commands.
8. Run `pnpm format`, `pnpm lint`, `pnpm typecheck`, then `pnpm coverage` and bring every workspace to at least 95% (lines, statements, branches, functions).

## Open questions / risks

- A set write failing after notes were pushed makes the sync throw although the notes are in; the next sync recomputes and fixes it. Accepted.
- `file` sets are shared by every folder, so syncing folder B overwrites the sets from folder A (same as the existing source-scoped model). Accepted for now; a per-folder key can come with custom sets.
- "today" uses the PC's local time zone; the cache holds ISO timestamps with no zone logic.
