# md-viz

Homelab TypeScript/Node project: loads markdown notes (a folder of `.md` files or a Bear DB) into a cache for analysis of content, relationships and structure. Currently the web app (a dashboard of cached note grids), an Electron app (pick a source, a folder of `.md` files or Bear, count its notes, sync them to the cache, show the last sync as three note grids), a design viewer, a shared UI package and a local note cache service (notes API over SQLite) and an API client package generated from the cache's OpenAPI spec exist. The web app shows the cached notes as a dashboard (one cell per note, coloured by its tags, hover shows the title and tags); the Electron app pushes notes to the cache; both have a theme switcher.

## Commands

Run from the repo root with pnpm:

- `pnpm dev` - web app dev server (port 5175)
- `pnpm dev:design` - design viewer dev server (port 5174)
- `pnpm dev:cache` - note cache service (port 8787, SQLite file in `apps/cache/data/`); see `apps/cache/README.md` for the API and curl examples
- `pnpm dev:all` - cache service, web app and Electron app together
- `pnpm generate` - generate the API client from the committed specs (`build`, `typecheck`, `test` and `lint` run it first)
- `pnpm openapi` - rewrite `apps/cache/openapi.json` from the cache's routes
- `pnpm dev:electron` - Electron app (electron-vite); its renderer uses port 5173 (the web app is on 5175, so both can run together)
- `docker build -f apps/cache/Dockerfile .` / `docker build -f apps/web/Dockerfile .` - build the deployable images from the repo root (see `deploy/README.md`)
- `pnpm build` / `pnpm typecheck` / `pnpm test` - run across all workspaces
- `pnpm coverage` - tests with v8 coverage in every workspace, one after another; fails below 95% (lines, statements, branches, functions) per workspace
- `pnpm lint` - ESLint with typed rules
- `pnpm format` / `pnpm format:check` - Prettier

Before finishing a change, run `pnpm format`, `pnpm lint`, `pnpm typecheck` and `pnpm coverage` (which runs the tests).

## Structure

- `apps/web` - React + Vite app (`@md-viz/web`): the dashboard, five independent floating `NoteGrid`s in a CSS grid that fills the window (`components/dashboard.tsx`): the automatic sets present in the cache (`created-today`, `created-last-30-days`, `modified-today`, `modified-last-30-days`, labels and order in `lib/dashboard-sets.ts`) in two columns, and all notes spanning both rows of a narrower third column; `main` has `px-4` to match the `AppHeader`'s `mx-4`. The source is derived from the cache's sets (`pickSource`: `bear` first, else `file`; the file source has no created sets, so those grids simply do not appear); `hooks/use-dashboard.ts` loads the notes (titles) and set summaries, each `SetGrid` loads its own set. The page dots follow the all-notes grid (it always holds the most notes); the other grids size themselves, so they do not share its lattice. No source switcher or click-through yet
- `apps/electron` - Electron app built with electron-vite (`@md-viz/electron`): `src/main` (node: window, dialogs and the IPC handlers only), `src/preload`, `src/renderer` (React), `src/shared/ipc.ts` (the IPC contract)
- `apps/cache` - Hono + `node:sqlite` note cache service (`@md-viz/cache`): `src/store.ts` (SQLite), `src/schemas.ts` (zod schemas), `src/app.ts` (routes), `src/openapi.ts` (spec), `src/index.ts` (server), `openapi.json` (committed spec)
- `apps/design` - design viewer for the theme tokens and shared components (`@md-viz/design`); display only, tokens live in `packages/ui`; routed with react-router (`BrowserRouter` in `main.tsx`, `<Routes>` in `app.tsx`, no `route.ts`). A floating top nav (`nav.tsx`) links the pages `/guidelines`, `/logo`, `/colors` (palette and every theme at once), `/typography`, `/spacing`, `/grid`, `/components` and `/explorations`, and carries the shared `ThemeSelect` (`useTheme` from `@md-viz/ui`, the apps' `md-viz-theme` key) so every page can be seen in all themes; there is no dark toggle. The page background is plain: a demo that needs the dots sits in a `DemoBox` (`bg-dots` box). `/components/<slug>` is one page per shared component (`src/component-pages/`: `registry.ts`, a side nav in `components-layout.tsx`, one `<name>-page.tsx` each with demos of its variants and states, headed by `PageHeading` and split by `DemoGroup`); adding a component is its page plus one line in the registry (and a test). Explorations are for design work that would crowd the pages. Each lives in its own folder `src/explorations/<slug>/` with everything it needs (components, data, an `index.ts` exporting its `Exploration`: slug, title, description and a `lazy` `Page`) and its tests in `tests/explorations/<slug>/`; adding one is a folder plus one line in `src/explorations/registry.ts`, served at `/explorations/<slug>` (an unknown slug shows a not-found card). An exploration imports `@md-viz/ui` and shared app code, never another exploration, and nothing but the registry imports from it
- `packages/api-client` - clients generated by hey-api from OpenAPI specs (`@md-viz/api-client`): one entry per API (`@md-viz/api-client/cache`, SDK and zod; the TanStack Query helpers are in `@md-viz/api-client/cache/react-query` so node code never bundles react-query), generated code in gitignored `src/generated/`; exports TypeScript source, no build step
- `packages/sync` - the note sync workflow without a UI (`@md-viz/sync`): types, loaders (`file`, `bear`), scan, the sync pipeline, automatic sets, state file and the `scanTarget` / `syncTarget` / `selectSource` / `loadLastSelection` / `rememberFolder` functions Electron's IPC forwards to; Node only, exports TypeScript source (`.` and the type-only `./types`), no build step, written for a future CLI too. Inside `src`: `pipeline/` (source-agnostic sync, `Note`, automatic sets), `sources/<name>/` (one folder per source: `index.ts` exports a single `SourceAdapter` (`load`, `scan`, `parse`, `key`, `remember`, `restore`) and is the only public file; the rest is private, and ESLint forbids importing it from outside the folder), `sources/index.ts` (the registry, `adapterFor`), plus `run.ts`, `target.ts`, `state.ts`, which never name a source; a new source is a folder plus one registry line (see its README; the `created-*` set rule in `pipeline/note-sets.ts` is the one source check left)
- `packages/ui` - shared shadcn components, the nine themes (Solarized light is the default) on a Tailwind v4 token set (Space Mono via `@fontsource`) and `cn` helper (`@md-viz/ui`); exports TypeScript source, no build step
- `deploy/` - the example `docker-compose.yml` users fetch with `wget` and edit, and its install README
- `demo/` - small committed set of markdown notes (18 counted, plus non-notes and a `.hidden/` dir) used as a scan target and test fixture; its README states the expected counts
- `create/` - logs and plans from `/create` and `/fix` sessions (a fix session is a create session with `Kind: fix` in its log header)

New apps go in `apps/*`, shared code in `packages/*`.

## Conventions

- File names are kebab-case everywhere (`note-grid.tsx`, `use-scan.ts`, `app.test.tsx`), components and tests included; the component inside is PascalCase. A test file is named after its source file. `unicorn/filename-case` enforces it in lint.
- One React component per file: every component definition lives in its own file (`react/no-multi-comp` enforces it). Exempt: shadcn-generated components in `packages/ui` (`card.tsx`) and `Cells` in `note-grid.tsx`, both with a lint override saying why. Any other case that seems to need an exception: stop and discuss it with the user instead of adding one.
- Unit tests treat one source file as the unit: one test file per source file in `tests/`, mirroring `src/`, mocking its dependencies only at the boundaries (react-query and SDK hooks, `window.api`, `electron`, `node:fs/promises` for failure paths, other packages when the unit just forwards to them), rendering small real children otherwise. `App` tests only check composition (what is shown, what is wired to what); behavior is tested where it lives. This is a trial, say so if it gets brittle.
- Coverage: every workspace must stay at or above 95% for lines, statements, branches and functions (thresholds in each `vitest.config.ts`/`vite.config.ts`, failing `pnpm coverage`). Entry files (`main.tsx`, Electron `main/index.ts` and preload, `apps/cache/src/index.ts`) and `src/generated` are excluded. Never lower a threshold or widen an exclusion to pass; raise it with the user. Run `pnpm coverage` workspaces one at a time (the root script does): parallel vitest runs race on `node_modules/.vitest-cache`.
- `eslint-plugin-react` is pinned with `settings.react.version: '19'` in `eslint.config.js`: `'detect'` crashes under ESLint 10.
- Source layout: `apps/web`, the Electron renderer (`apps/electron/src/renderer/src`) and `packages/ui` keep React components in `components/`, hooks (`use-*.ts`) in `hooks/` and everything else that is neither (helpers, constants, clients) in `lib/`; only the entry files (`main.tsx`, `app.tsx`, the ui `index.ts`) sit at the root of `src`. Tests mirror it: `tests/components/`, `tests/hooks/`, `tests/lib/` (the Electron renderer's under `tests/renderer/`), with `app.test.tsx` at the top. `apps/design` is deliberately exempt: it keeps its own structure (`sections/`, `component-pages/`, `explorations/`). Electron's `src/main` is Node code and has no such folders.
- Tests live in a `tests/` folder beside `src/` in each workspace, never inside `src/`. Vitest + Testing Library + jsdom.
- Shared UI belongs in `packages/ui`; loading, empty and error states are `Loader`, `EmptyState` and `ErrorState` (each inside a `StateBlock`, which floats on the page like `NoteGrid`, `fill` to centre it in its container), so don't write another: `Loader` picks one of the `loaderFills` at random when it mounts and keeps it, has only an aria label and draws note-palette squares; `ProgressBar` (value, max, label) is a square bar for a known total; `EmptyState` is the palette ghost (`compact`: a small muted ghost with no text, for small blocks); `ErrorState` is the broken tile, takes `detail`, `onRetry` (shows `try again`, pass it only when a retry is possible) and `action`; the design exploration `states` records the options that were considered; apps hold only app-specific code and import from `@md-viz/ui`.
- `Select` (shadcn, `select.tsx`, several components in one file like `card.tsx`) follows the "inputs and focus" guideline. Add shadcn components with the CLI from `apps/web` (`pnpm dlx shadcn@latest add <name>`); they land in `packages/ui/src/components`. Export them from `packages/ui/src/index.ts` and run `pnpm format`. The CLI's generated components import `cn` from the `cn` package.
- Design decisions are recorded as guidelines on the design board (`apps/design/src/sections/guidelines.tsx`); follow them in any UI: all text lowercase, square edges (every radius token is 0), dot grid page background. Change tokens in `packages/ui/src/styles/globals.css` (the Solarized light defaults) and the themes in `packages/ui/src/lib/themes.ts`, never per app. Update the guidelines list when a decision changes.
- The logo (`Logo`, `Wordmark`) is pixel art drawn from bitmap glyphs in `packages/ui/src/lib/pixel-glyphs.ts`: the icon is `.md` on a tile, the wordmark is `md-viz` with each cell drawn as a 2x2 block of small squares and `viz` in the primary color; `AppHeader` shows the wordmark and floats on the page (centered, margin, border, hard shadow, sticky below the top edge) instead of spanning the full width. The favicons (`apps/*/public/favicon.svg`) are static copies with fixed Solarized hex colors, so regenerate them by hand when the glyphs or theme change; `apps/web/tests/favicon.test.ts` catches drift in the pixels.
- The page background is the `bg-dots` utility: a dot every `--grid-size`, starting at `--grid-origin-x/y` (default the page corner). The web app sets those vars (`useGridLattice` in `@md-viz/ui`) so the dots land on the corners of the note squares: `NoteGrid` reports its cell (`onCellChange`) and the spacing is `latticeSpacing(cell)` (the cell, a whole multiple of it below 16px, or the cell divided evenly when over 32px). With several note grids the one with the most notes sets the cell and the rest pass `cellStep` so they use whole multiples of it; the web dashboard sizes its grids independently and only the all-notes grid sets the dots. `useDotLattice` (`@md-viz/ui`) sets the lattice from the first square of the grid block it is given; `useGridLattice` wraps it with the ref and cell state (`{ ref, cell, onCellChange }`: pass `ref` and `onCellChange` to the reference `NoteGrid`), and `DEFAULT_NOTE_COLOR` is the neutral grey (the last palette colour) that notes without tags get. The Electron app's three status grids (`sync-grids.tsx`) use it: fixed-width columns (272px, `src/shared/window-size.ts`), blocks start at the column's top (the last one is pinned right, so its edge meets the status card's, and that column is off the dots by the leftover width), the biggest grid is the reference, the others pass `cellStep={latticeSpacing(cell)}` and the column pitch is the largest whole number of dot spacings that keeps a gap of at least 16px within the fixed window (`columnPitch`; else the plain 32px gap and the columns are off the dots). The page must not scroll (the dots do not move with it).
- Components that draw thousands of items (like `NoteGrid`) must not attach per-item elements, handlers or popovers: use one pointer handler that derives the item from the layout, one shared tooltip, and `React.memo` on the item layer.
- `NoteGrid` is always a block floating on the page background with its own hard shadow (`bg-card shadow-hard`), never on or inside a card. It fills its container when `height` is omitted (pass `height` for a fixed size); `align="start"` pins it to the container's top-left and `align="end"` to its top-right instead of centring. `label` hangs a label card (with the count) above the block, as wide as the grid, and adds 42px above the drawing area for it. An empty `notes` array shows a block with an `EmptyState` (`compactEmpty` for the compact one, used by the Electron status grids) that is `emptySize` (px) or else fills the drawing area less the 3px stroke room. The Electron status grids do not pass it: an empty one fills its column like any other (`gridHeight`). `ref` is the block, for `useDotLattice`. Squares are whole pixels, so the block is exactly as wide as its squares and the leftover space is page background. The one shared tooltip is centred above the hovered cell and, after render, moved sideways (`tooltipShift` in `packages/ui/src/lib/tooltip-shift.ts`, 8px margin) so it stays inside the window (measured with `documentElement.clientWidth`, the viewport less any scrollbar: against `innerWidth` a tooltip under a scrollbar overflows the page, which adds the scrollbar and resizes the grid, and it flickers): near the left edge it flows right, near the right edge left. The grid has no border: the 4px hover outline is centred on the cell edge and the svg is `overflow-visible`, so on an edge cell it reaches past the block.
- Any app that uses the UI package needs `@source` for `packages/ui/src` in its CSS so Tailwind sees the class names.
- Electron IPC: every channel, payload type and the `window.api` shape live in `apps/electron/src/shared/ipc.ts`; main registers handlers, preload only forwards, the renderer sees just `window.api`. Keep `contextIsolation` and `sandbox` on, `nodeIntegration` off. Filesystem work stays in main. A sandboxed preload must be CommonJS, hence the `.cjs` output in `electron.vite.config.ts`; `Api` members are function-typed properties (not methods) to satisfy `unbound-method`.
- `apps/electron` has two tsconfigs so each side only sees its own environment: `tsconfig.node.json` (main, preload, shared, `tests/main`) and `tsconfig.web.json` (renderer, shared, `tests/renderer`). Put new tests in the matching folder. The Electron binary is downloaded on first run, not at install.
- Electron renderer (`apps/electron/src/renderer/src`): `app.tsx` only composes. State lives in hooks (`hooks/use-scan.ts` for the chosen source (a `SyncTarget`) and its note count, `hooks/use-sync.ts` for syncing and the last sync) that take an `onError` callback; the single error string and the selected source stay in `App`, which shows a saved selection with `open` (Bear is scanned at once, a file source only with a folder). `SourceSelect` (the `Select` from `@md-viz/ui`, `file` / `bear`), `FolderCard` (one line: source and last synced, the note count at the end), `SyncGrids`, `StatusGrid` and `SyncOverlay` (in `components/`) are presentational, and `choose folder` shows only for `file`. The window is fixed (`src/shared/window-size.ts`, 912x520 content, not resizable, just wide enough for three 272px columns), so the header and card are simply full width and the grids are always shown (empty before a sync); a grid of 12 notes or fewer keeps a 160px drawing height (`gridHeight`: 6 notes are 3 wide, 2 tall), one of more fills the height left. While scanning or syncing `SyncOverlay` (loader, a line, a `ProgressBar` when the total is known, the counts the pipeline reports) covers the grids with a semi-opaque veil (`role="dialog"`), and an error replaces the grids; layout helpers are in `lib/sync-layout.ts`. The explorations `states` and `sync-layout` record the options that were considered.
- Electron sync: all of it lives in `packages/sync` (see its README for the types, the workflow and how to add a source); Electron's `src/main/ipc.ts` only forwards. Every source is a loader that returns `{ notes: Note[], failed: string[] }` and one pipeline, `syncNotes(source, loaded, options)`, does the rest and never branches on source; `failed` notes are neither pushed nor deleted, and nothing is deleted or recorded when loading or the cache listing fails. The sync uses the generated cache SDK; the caller passes the cache URL (Electron reads `CACHE_URL`, default `DEFAULT_CACHE_URL`, `http://localhost:8787`) and the package never reads it. `electron.vite.config.ts` bundles `@md-viz/api-client` and `@md-viz/sync` into main (both are TypeScript source), and `tsconfig.node.json` includes the `DOM` lib because the generated client references `BodyInit`. The renderer imports the shared types only through `@md-viz/sync/types` (re-exported by `src/shared/ipc.ts`) because its tsconfig has no Node types.
- Electron window: fixed content size from `src/shared/window-size.ts` (`useContentSize`, not resizable, maximizable or fullscreenable), `titleBarStyle: 'hidden'`, the `AppHeader` is the drag region (`index.css` sets `-webkit-app-region`, with `no-drag` on its buttons, links and inputs) and gets `pl-24` on macOS (traffic lights) or `pr-40` elsewhere (`titleBarOverlay`). In dev the Dock, Cmd-Tab and menu bar name stay "Electron" because macOS reads it from the Electron binary's `Info.plist`; only packaging (`productName`) changes that, while the icon can be set at runtime.
- Electron app icon: `apps/electron/resources/icon.png` is the `.md` tile (the web favicon) scaled to 1024px by `apps/electron/scripts/make-icon.mjs`; regenerate it by hand with `node apps/electron/scripts/make-icon.mjs` when the glyphs or theme change. Main sets it as the dock icon (macOS) and window icon (windows, linux); a packaged app will need an `.icns`/`.ico` made from it.
- Themes: a theme (`packages/ui/src/lib/themes.ts`: id, name, `ui` roles and eight `hues`) is one fixed look for the whole UI; there is no light/dark matching (the `.dark` class and its tokens in `globals.css` are no longer used by any app, the design viewer's toggle is gone). `applyTheme` sets the tokens (`--background`, `--card`, `--primary`, `--border`, `--focus` (keyboard focus ring and border, the hovered cell outline, the select popup border), `--shadow-color` (the hard shadow), `--note-stroke`, `--grid-dot`, ...) and `--note-0..24` on `<html>`; `globals.css` holds the Solarized light values as the default. `useTheme` (`@md-viz/ui`) applies the chosen theme before paint and keeps the choice in `localStorage` (`md-viz-theme`), and `ThemeSelect` is the switcher in both apps' headers. A theme's focus colour is at least 3:1 against its page and card and clearly apart from its primary, and its shadow at least 2:1 against the page (tested in the design exploration `note-palettes`, which records the options that were considered, including the dropped themes). Never hard-code black, white or a Solarized colour in a component: use a token. The 25 note colours are `noteColors(theme)` (`lib/note-palette.ts`): the hues in three strengths in an order that keeps neighbours apart, then the neutral grey; loaders and icons cycle through the eight full hues (`ACCENT_COLORS`).
- Tag colours: a `Note` for `NoteGrid` is `{ id, title, colors, tags? }`; `colors` are palette indexes, one per tag, and the grid draws the first three as horizontal stripes inside the gridlines (`lib/tag-stripes.ts`), none as the neutral grey, and the tooltip lists all `tags`. Only the top level of a nested tag is coloured (`daily/10/28` is `daily`; the tooltip still lists the full tags): the sync (`packages/sync/src/pipeline/tag-colors.ts`) gives every top-level tag without a colour the least-used of the 24 hue colours when it syncs and keeps it, the apps look a note's colours up with `tagColorIndexes` (`@md-viz/ui`: one colour per distinct top-level tag), the cache stores the mapping (`/tag-colors`) and never interprets it, and the apps resolve index to colour through the current theme, so switching themes recolours without touching the cache. Bear lists every level of a nested tag (`daily`, `daily/10`, `daily/10/28`), so its loader keeps only the deepest one; a cached note keeps the tags it was synced with until it changes, so after changing how tags are read, delete `apps/cache/data/` (cache stopped) and sync again. The web app reads the mapping from the cache; Electron's status grids use the one saved with the last sync in `state.json` (`LastSync.tagColors`, and `tags` on each `NoteRef`). The sync package keeps its own `TAG_COLOR_COUNT` and `topLevelTag` (a test in Electron checks they match the UI's `HUE_COLORS` and `topLevelTag`).
- Electron state: `state.json` in Electron's `userData` (path passed to the package as `stateFile`; format and keys in the `packages/sync` README) holds the last selected source, the last folder chosen for files and the last completed sync per `syncKey`. The IPC takes a `SyncTarget` for `scan` and `sync`, validated in the package (`parseTarget`); `selectSource` and `loadLast` return a `LastSelection` and the renderer opens it on launch. Kept local on purpose, it may become a history log in the cache DB.
- `apps/cache` runs TypeScript directly with Node's type stripping (no build step): use `.ts` import extensions and erasable syntax only (no enums or namespaces). Notes are stored as `(note_id, field, value)` rows; `synced` is the one field the service stamps itself. The fields the Electron sync writes are `title`, `body`, `tags` (JSON array string), `created`, `modified` and `source` (`file` or `bear`); the cache does not interpret them. Keep `node:sqlite` inside `store.ts` (it is still experimental). Sets (`/sets`, tables `sets` and `set_notes`) are named groups of note IDs stored exactly as pushed and cleaned of a note when it is deleted; the cache never derives them. Tag colours (`/tag-colors`, table `tag_colors`) are `(tag, color index)` rows; `POST` only adds tags that have no colour yet, so a tag keeps its colour, and the cache does not interpret the index.
- API contracts flow one way: zod routes in the server (`@hono/zod-openapi`) -> committed `openapi.json` (`pnpm openapi`; a test fails when stale) -> generated client in `packages/api-client` (`pnpm generate`; gitignored output; SDK and hooks validate requests and responses with the generated zod schemas). Never hand-write fetch calls or response types for our own APIs; change the route, regenerate. Use the TanStack Query helpers (`listNotesOptions` etc.) in React and the SDK functions elsewhere. A workspace script run directly needs `pnpm generate` done once; the root scripts do it. Keep response shapes to fixed keys (put dynamic keys in a record under a named property like `fields`): the hey-api zod plugin ignores `additionalProperties`, and zod then strips the extra keys. In tests the generated client needs a base URL (`configureCacheClient`) because node cannot build a `Request` from a relative URL; `apps/cache/openapi.json` is in `.prettierignore` because the staleness test compares exact bytes. See `packages/api-client/README.md` for adding an API.
- Docker deployment: two images built from the repo root and published to GHCR by `.github/workflows/publish-images.yml` on every push to `main` (`ghcr.io/dannywieser/md-viz-cache` and `md-viz-web`, `latest` + commit SHA, `linux/amd64` only). `apps/cache/Dockerfile` runs `node src/index.ts` (`CACHE_DB=/data/cache.db`, `/data` is a volume, `pnpm deploy --legacy` because pnpm 10 refuses a plain deploy). `apps/web/Dockerfile` builds the app and serves it with nginx, which also proxies `/api/` to `CACHE_UPSTREAM` (default `cache:8787`, prefix stripped, re-resolved per request so a recreated cache is picked up); the web app's cache base URL therefore defaults to the same-origin `/api` and the Vite dev server proxies `/api` to `CACHE_URL` (default `http://localhost:8787`). `.dockerignore` keeps the context small, so a new workspace the images need must not be excluded there. `deploy/docker-compose.yml` is the user-facing base file; the author's homelab runs it behind Caddy at `md-viz.dgwlab.net`. The cache has no auth: LAN/VPN only.
- Dependency versions shared by several workspaces (currently `zod`, `@tanstack/react-query`) live in the `catalog:` of `pnpm-workspace.yaml`; reference them as `"catalog:"`.
- TypeScript is pinned to 6.0.x because typescript-eslint does not support TypeScript 7. Do not upgrade `typescript` until it does.
- Prettier: no semicolons, single quotes, trailing commas, 100 columns. 2-space indent, LF.
- Don't commit unless asked, except in `/create` and `/fix` sessions: they work on their own `create/<slug>` or `fix/<slug>` branch and commit, push and open/ready the PR themselves (see `create/README.md`).
